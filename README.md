# Yandex Reviews

Приложение для подключения организации на Яндекс Картах и загрузки её отзывов. Репозиторий состоит из двух
независимых приложений:

- `backend` — Laravel API;
- `frontend` — Vue 3 SPA.

## Ссылки

- [Репозиторий на GitHub](https://github.com/darkselia/yandex-organization-widget)
- [Демо на darkselia.ru](https://darkselia.ru) — домен, на котором будет опубликован рабочий прототип. После деплоя
  здесь будет указан точный адрес приложения.

## Требования

Для запуска без Docker потребуются:

- PHP 8.4 с расширениями `pdo_sqlite` и `sqlite3`;
- Composer 2;
- Node.js 24 и npm;
- SQLite.

Альтернативный вариант — Docker с поддержкой Docker Compose.

## Локальный запуск

Подготовьте backend из корня проекта:

```powershell
cd backend
composer setup
```

Команда создаст `.env` из `.env.example`, если файла ещё нет, создаст SQLite-базу, сгенерирует `APP_KEY` и выполнит
миграции.

Подготовьте frontend:

```powershell
cd ..\frontend
Copy-Item .env.example .env
npm install
```

Запустите приложения в отдельных терминалах.

Laravel API:

```powershell
cd backend
composer serve
```

Обработчик очереди:

```powershell
cd backend
composer queue
```

Команда запускает `queue:listen`: в режиме локальной разработки Laravel заново
загружает код приложения перед каждым заданием. Окно с обработчиком должно
оставаться открытым, иначе новые запуски останутся в статусе `queued`.

Vue:

```powershell
cd frontend
npm run dev
```

После запуска доступны:

- frontend: <http://localhost:5173>;
- API: <http://localhost:8000>;
- healthcheck: <http://localhost:8000/up>.

## Запуск через Docker

Создайте локальные env-файлы:

```powershell
Copy-Item backend\.env.example backend\.env
Copy-Item frontend\.env.example frontend\.env
```

Соберите образы и выполните первоначальную настройку Laravel:

```powershell
docker compose build
docker compose run --rm api composer setup
```

Запустите API, queue worker и frontend:

```powershell
docker compose up
```

Docker использует долгоживущий `queue:work`. После изменения PHP-кода задания
перезапустите контейнер очереди, чтобы worker загрузил новую версию классов:

```powershell
docker compose restart queue
```

При ручном запуске через `php artisan queue:work` выполните после изменения кода:

```powershell
cd backend
php artisan queue:restart
```

Для остановки используйте `Ctrl+C` или выполните:

```powershell
docker compose down
```

SQLite-файл хранится в `backend/database/database.sqlite`. API и queue worker используют один и тот же файл.

## Переменные окружения

Основные переменные backend:

- `APP_URL` — адрес Laravel API;
- `FRONTEND_URL` — origin Vue-приложения для CORS;
- `SANCTUM_STATEFUL_DOMAINS` — адреса SPA, которым разрешена cookie-аутентификация;
- `DB_CONNECTION=sqlite` — локальная база данных;
- `SESSION_DRIVER=database`, `CACHE_STORE=database`, `QUEUE_CONNECTION=database` — хранение сессий, кэша и очереди в
  SQLite.

Frontend использует `VITE_API_URL` как базовый адрес API.

Переменные, которые относятся к запросам в Яндекс Карты:

- `YANDEX_CONNECT_TIMEOUT_SECONDS` — сколько ждать установления соединения;
- `YANDEX_TIMEOUT_SECONDS` — общий таймаут одного запроса;
- `YANDEX_REQUEST_DELAY_MS` — минимальная пауза между страницами отзывов.

## Тестовый пользователь

После `composer setup` пользователь создаётся автоматически. Для существующей базы его можно создать или обновить
отдельно:

```powershell
cd backend
php artisan db:seed
```

Данные по умолчанию:

```text
Email: demo@example.com
Пароль: demo-password
```

Значения задаются через `SEED_USER_NAME`, `SEED_USER_EMAIL` и `SEED_USER_PASSWORD`. Они опубликованы в `.env.example`

## Модель данных

- `users` хранит пользователя для входа;
- `organizations` хранит только успешно проверенные карточки: ссылку, внешний ID, название, рейтинг и точные счётчики;
- `reviews` хранит отзывы и защищена от дублей уникальной парой организации и внешнего ID. Поле `last_seen_at`
  показывает, во время какой успешной синхронизации отзыв был замечен в последний раз;
- `parse_runs` хранит URL, состояние, прогресс и результат каждой попытки фоновой синхронизации. До успешного парсинга
  запуск не связан с организацией;
- `organization_snapshots` хранит рейтинг и счётчики на момент успешного запуска. Каждый новый снимок связан с создавшим
  его `parse_run`.


## 1. Устойчивость к смене разметки.

Парсер не возвращает пустой успешный результат, если не нашёл ожидаемые данные. Mapper проверяет обязательные секции,
типы полей, ID организации, номер страницы, диапазон оценки и принадлежность отзыва нужной карточке.

Ошибки разделены по причинам:

- `source_schema_changed` — исчезло обязательное поле или script с состоянием;
- `empty_source_response` — источник вернул пустую страницу;
- `invalid_source_data` — данные есть, но противоречат ожидаемому формату;
- `source_blocked` — получена CAPTCHA или HTTP 403;
- `source_rate_limited` — Яндекс вернул HTTP 429;
- `source_unavailable` — таймаут, ошибка соединения или другой неуспешный HTTP-ответ.

Техническая причина сохраняется в `parse_runs.error_message` и попадает в лог. Основные варианты структуры проверяются
автоматическими тестами на сохранённых ответах Яндекса, поэтому изменение схемы будет видно как упавший тест или запуск
со статусом `failed`, а не как «успешная» загрузка пустой организации.

## 2. Обоснование подхода к парсингу.

Я выбрала разбор JSON, который Яндекс вкладывает в HTML страницы отзывов. Клиент последовательно открывает
`/reviews/?page=1`, `/reviews/?page=2` и так далее, а mapper переводит нестабильную структуру Яндекса в собственные DTO
приложения.

Парсер не ограничивается первой страницей. Он продолжает работу, пока не выполнится одно из условий:

- Яндекс сообщил, что отзывов больше нет;
- закончились страницы;
- следующая страница оказалась пустой;
- получено заявленное количество доступных отзывов;
- достигнут защитный предел в 600 отзывов.

Разбор встроенного JSON быстрее, проще тестируется на сохранённых fixtures и не требует запускать браузер для каждой
страницы. Цена такого решения — зависимость от внутренних полей Яндекса и класса script-тега. Если Яндекс изменит
эту часть страницы, mapper придётся обновить.

Headless-браузер ближе к поведению обычного пользователя и иногда лучше проходит страницы, которые полностью собираются
JavaScript-кодом. Но для этой задачи он заметно тяжелее: требует Chromium, больше памяти, дольше запускается и сложнее
масштабируется на десятки организаций.

Для рабочего сервиса я бы оставила текущий способ основным. При
возможности можно еще дополнительно реализовать headless-браузер для работы в случаях, когда основной способ не
работает.

## 3. Масштаб и фоновая обработка.

Одна организация может потребовать около двенадцати внешних запросов, поэтому парсинг не выполняется внутри HTTP-запроса
пользователя. API быстро создаёт `parse_run`, возвращает `202 Accepted`, а `SyncYandexOrganizationJob` работает
отдельно.

У запуска есть состояния `queued`, `running`, `retrying`, `succeeded` и `failed`. После каждой страницы job обновляет
`reviews_fetched` и `reviews_expected`. Временные ошибки соединения, блокировка и ограничение частоты повторяются до
трёх раз с паузами 60 и 300 секунд. Таймаут одного задания — 600 секунд, а `DB_QUEUE_RETRY_AFTER` выставлен больше этого
времени, чтобы одно долгое задание не было взято двумя worker-ами одновременно.

Для прототипа используется database queue: её легко поднять вместе с SQLite. Для сети из 50 филиалов я бы перенесла
очередь в Redis, добавила Laravel Horizon, отдельные очереди по источникам, мониторинг зависших заданий и ограничение
общей параллельности. Сама схема API при этом не изменится.

## 4. Анти-бан на объёме.

Сейчас запросы одной организации выполняются последовательно, между ними выдерживается настраиваемая пауза. Клиент
сохраняет cookies, отправляет браузерный User-Agent, распознаёт CAPTCHA и отдельно обрабатывает 403 и 429. После
временной блокировки job не начинает бесконечно атаковать источник, а уходит в отложенную повторную попытку.

Для регулярного обновления десятков филиалов этого недостаточно. В production я бы добавила:

- общий rate limiter в Redis для всех worker, а не только паузу внутри одного задания;
- случайный разброс интервалов, чтобы запросы не выглядели как ровный автоматический поток;
- пул прокси с контролем качества и временным исключением заблокированных адресов;
- метрики по доле ошибок, времени ответа и количеству заблокированных запросов.

## 5. Идемпотентность и история изменений.

Организация определяется парой `source + external_id`, отзыв — парой `organization_id + external_id`. Повторный парсинг
обновляет существующие строки через `updateOrCreate`, поэтому одна и та же карточка или отзыв не дублируются.

После успешного запуска всем полученным отзывам записывается одинаковый `last_seen_at`. API показывает только отзывы,
замеченные во время последней синхронизации. Если старый отзыв перестал входить в доступные Яндексом последние 600, он
остаётся в базе для истории, но больше не попадает в актуальный список.

Снимки сортируются по `captured_at`. Чтобы получить изменение, достаточно взять два соседних снимка одной организации и
вычесть из нового значения предыдущее. `parse_run_id` связывает снимок с конкретным успешным запуском и его
диагностикой. Даже если значения не изменились, новый снимок сохраняется: он подтверждает, что карточка была проверена в
этот момент, а нулевая разница тоже является результатом.

## Что я бы доделала, имея больше времени

В первую очередь я бы добавила регулярное обновление организаций по расписанию, Redis/Horizon и мониторинг очереди.
Затем — глобальный throttling, управляемый пул прокси, резервный headless-парсер.

Для пользователя я бы сделала экран истории изменений рейтинга и счётчиков, отметки новых и исчезнувших отзывов.. 
Для качества проекта пригодились бы end-to-end тесты полного сценария в браузере и отдельный
smoke-тест реального Яндекса, запускаемый по расписанию, а не при каждом CI-сборочном запуске.
